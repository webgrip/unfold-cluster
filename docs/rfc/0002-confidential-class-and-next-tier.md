## Summary

RFC 0001 secures the cluster against its own workloads and against outsiders. This RFC covers two things it leaves open:

1. **The confidential class.** Client code, the Run's credentials and its output stay protected from the hosting provider and from Unfold's own administrators, and a client can verify that with a signed hardware report. It is buildable on Talos today, with conditions this RFC names.
2. **The next tier.** These measures close the gaps an attentive reviewer finds in RFC 0001. Some of them belong before the first client.

## Part 1: the confidential class

### What the hardware protects, and what it does not

AMD SEV-SNP encrypts a VM's memory and protects its integrity against the hypervisor. The CPU signs a report of what was launched (firmware, kernel, command line, initial data), and that report chains to AMD's root key. Talos's kernel supports SNP as a host. It does not support Intel TDX: `CONFIG_INTEL_TDX_HOST` is unset. The confidential class is therefore SNP-only.

It does **not** protect:

| Not protected | Consequence for the design |
| --- | --- |
| Disk and network I/O | The host sees every byte through shared bounce buffers. Everything leaving the guest is encrypted end to end |
| The Kubernetes control plane | It still sees the pod spec, status, events and flows. The pod spec is a fixed, signed template; nothing sensitive goes in it |
| Availability and scheduling | The host can starve or kill the VM. Accepted |
| Bugs inside the guest | The agent can still be wrong or hostile. Every other layer stays on |
| Physical attacks on memory | Interposer attacks on DDR5 (TEE.fail, October 2025; DDRop, September 2026) read or corrupt protected memory with under $1,000 of hardware and have no fix. The protection holds against remote and software access by the provider, not against a determined insider with the server in hand |
| Firmware bugs | Several 2024–2026 SNP flaws (BadRAM, RMPocalypse, StackWarp, Fabricked, AMD-SB-3030) are fixed only by firmware the provider must install. The verifier enforces a minimum firmware level and refuses machines below it |
| SMT | StackWarp (January 2026) works through the sibling hyperthread. SMT is off on confidential nodes, and the guest policy forbids it |

### The two holes the obvious design leaves

1. **The model gateway.** The agent's prompts contain client code, and today they pass through LiteLLM in the untrusted cluster. For this class, model traffic leaves the guest directly to the provider over TLS. If a gateway is kept, it runs inside a confidential VM too. The model provider and the forge still see the code; that is stated to the client, not hidden.
2. **Who runs the key broker.** The broker decides which guests receive keys. If it runs in the cluster, the cluster's administrator can change its rules. It runs outside the cluster (below).

### How a confidential Run works

| Step | What happens |
| --- | --- |
| 1. Fixed template | Each pod size has one pod spec and one policy, generated by `genpolicy` and signed. The host never chooses Run parameters. The vCPU count is part of the launch measurement, so sizes are fixed per RuntimeClass |
| 2. Launch | Kata starts the guest on `kata-qemu-snp`. The guest's agent enforces its policy: no exec, no logs, no attach, no copy from the host |
| 3. Attest | The guest proves its launch measurement and initial data to the key broker (Trustee) |
| 4. Assignment | Only an attested guest receives its assignment from the broker: repository, task and a short-lived forge token scoped to one branch, signed by the dispatcher or the client |
| 5. Work | The repository is cloned into guest memory. Images are pulled and verified inside the guest. Model calls go straight to the provider |
| 6. Deliver | The guest pushes to the forge and attaches a receipt: a fresh hardware report over `run id ‖ commit ‖ nonce`. The client checks it against AMD's keys themselves |
| 7. Observe | Only a fixed list of content-free events leaves the guest (phase, timings, token counts, exit code). Anything with content is encrypted to the client's key |

### Where the key broker lives

| Option | Protects against | Cost | Weakness |
| --- | --- | --- | --- |
| A. In the homelab | Hetzner | About €0 | The owner is still trusted; the homelab becomes a dependency of every confidential Run |
| **B. Inside a confidential VM at a second provider (IONOS, Frankfurt)**, its own measurement published, rule changes only through signed, append-only updates | Hetzner and Unfold's operators | About €83 a month | One more system to run |
| C. Run by the client | Everyone except AMD, the image builder and the model provider | The client's | Onboarding effort |

**Proposed: B by default, C as a premium tier.**

### Talos specifics

- **The extension.** `kata-containers-snp` (Talos extensions v1.14.0) ships the SNP firmware, guest kernel and verified root image from Kata 3.32.0, with the handlers `kata-qemu-snp` and `kata-qemu-coco-dev`. A contributor validated it on bare-metal AMD Turin with a matching launch measurement. Talos CI covers only the development handler.
- **Version skew.** Confidential Containers v0.23 is built on Kata 4.2; the Talos extension is on 3.32. The key broker must match the guest components in 3.32 until the Kata 4 work (RFC 0001) lands.
- **Annotations.** The SNP extension also forwards every `io.katacontainers.*` annotation. Two advisories make that dangerous on the host: GHSA-37rf-pj8c-g5g3 (agent and runtime annotations slip past the allowlist) and GHSA-mp2j-xm59-qfgw (`config_path`). Confidential Containers needs exactly one annotation, `io.katacontainers.config.hypervisor.cc_init_data`, to carry its initial data. The admission guard gets a narrow carve-out: that one key, only with an SNP or development runtime class. Everything else stays refused, including vCPU and memory overrides, which would change the measurement anyway.
- **Guest policy.** Kata's default SNP guest policy allows SMT and does not disable page swapping, which the Heracles attack exploits. Both are overridden.

**Verifying a rented box before trusting it.**

1. In the rescue system, `dmesg` shows SEV-SNP enabled, and `/sys/module/kvm_amd/parameters/sev_snp` is `Y`. `snphost ok` and `snphost show tcb` report the firmware level.
2. On a test guest, `snpguest report` with a fresh nonce.
3. On a trusted machine, fetch AMD's certificates, verify the report's chain, recompute the launch measurement with `sev-snp-measure`, and check the firmware level and platform flags (memory alias check on, SMT off).

### Cost and performance

- **Memory:** about 4–7% less memory bandwidth, and slower first-touch allocation.
- **Start time:** boots take two to three times longer, and guest image pulls add more.
- **Network:** network throughput under load drops by about 20% through bounce buffers.
- **Pinned memory:** each confidential VM reserves its whole memory up front, so a confidential node runs fewer Runs.

### Phases

| Phase | What | Trust anchors | Extra per month | What a client can verify |
| --- | --- | --- | --- | --- |
| 0 | The pipeline on the AX41: `kata-qemu-coco-dev`, a key broker in the homelab, `genpolicy` templates, the admission carve-out. **No confidentiality** | None | €0 | Nothing |
| 1 | One SNP node (AX162), SMT off, verified in rescue before install; the hardened guest policy | AMD; Kata's published images; the homelab broker | from €319 | A real hardware report whose measurement they can recompute from published images |
| 2 | The key broker in an IONOS confidential VM with a published measurement and signed rule updates; forge and model keys released only to attested guests; per-Run receipts; optional client-run broker | AMD; the image builder; the broker image | about +€83 | Their own check of every receipt against AMD's keys; the broker's measurement; with a client-run broker, keys that never leave them |
| 3 | A confidential judge model on a confidential GPU (GCP H100 in the Netherlands, on demand) | + NVIDIA | about €600 for 50 hours | A combined CPU and GPU report |

Phase 0 has no hardware cost and builds everything the later phases need. Phase 1 starts when a client contract asks for protection from the provider.

## Part 2: the next tier

### The hole in RFC 0001

Only the owner may push straight to `main` (ADR-0050). A check that runs only on pull requests never sees such a push, so every policy test is advisory for the most privileged writer.

**Fix:** CI signs an attestation, "policy tests passed for commit X", and Flux reconciles only commits that carry it. The gate then holds for every push, the owner's included. A second person's approval is required on the policy, RBAC and network paths once there is a second person.

### Measures

| When | Measure | Threat it closes |
| --- | --- | --- |
| Before the first client | FIDO2 hardware keys on every admin, forge, cloud, DNS and tailnet account | Phished passwords and app codes |
| Before the first client | The age backup key, signing keys and Talos CA on hardware tokens; OpenBao recovery split two-of-three across tokens in separate places; a written two-person break-glass rule, every use logged to the write-once store | Copied key files; one person as the only key |
| Before the first client | Two-phase Runs: secrets and egress only while dependencies install, then the agent works with neither | An agent carrying credentials or data out |
| Before the first client | A git proxy that checks the operation (repository, branch, force-push), not only the credential | A valid token used for the wrong push |
| Before the first client | A secret and PII scan on every diff, PR body and outbound payload | A secret from repository A committed into repository B |
| Before the first client | A prompt-injection test suite (AgentDojo, InjecAgent) run against our harnesses in CI, and a review of every tool against the lethal trifecta: private data, untrusted content and an exfiltration channel together | Repository text steering the agent |
| Before the first client | A retention schedule and crypto-shredding on contract end; data processing agreements and a sub-processor list | Keeping client data longer than needed |
| Before the first client | Incident runbooks with the reporting clocks (GDPR 72 hours; the Cyber Resilience Act's 24 and 72 hours for exploited vulnerabilities), a quarantine label that cuts a pod off without deleting it, and a first tabletop exercise | The first bad day without a script |
| Before the first client | `SECURITY.md` and `security.txt`; an external test of the Run boundary | Nobody can report a flaw; nobody outside has tried |
| Before the first client | Patch deadlines: actively exploited vulnerabilities (CISA KEV) within 14 days, the rest ranked by EPSS | Known holes left open |
| Before ten clients | The attested-deploy gate above; second-person review on policy paths | The owner bypassing every check |
| Before ten clients | CI in a fresh VM per job, split by trust level; build provenance (SLSA) checked at admission | A poisoned build step |
| Before ten clients | Per-tenant encryption keys, egress addresses and anomaly baselines | One tenant's data or traffic mixed with another's |
| Before ten clients | An external service-account signer, pod certificates, just-in-time admin; no long-lived tokens anywhere | Stolen long-lived credentials |
| At scale | An HSM-backed OpenBao seal; a dedicated node per tenant; remote attestation of bare-metal nodes (Keylime); ISO 27001; a red team; a bug bounty; reproducible builds | Weaknesses that matter once many clients depend on us |

### Skipped, and why

- **Self-hosted Sigstore (Fulcio and Rekor):** heavy to run; keys on hardware give most of the benefit.
- **A service mesh now:** duplicates WireGuard and Cilium identity.
- **A full SIEM:** VictoriaLogs, vmalert and ported Sigma rules suffice at this size.
- **Falco next to Tetragon:** two sensors doing the same job.
- **Keylime on cloud VMs:** they have no TPM to attest.
- **SOC 2 before ISO 27001:** EU clients ask for ISO.
- **Deploy freezes:** ceremony without a threat they close for a team this size.
- **A paid bug bounty before there is time to triage:** it produces noise.

### Compliance notes

These are not legal advice.

- **NIS2:** the Dutch Cyberbeveiligingswet has been in force since 15 August 2026. Below 50 staff and €10 million turnover, Unfold is likely out of scope, but in-scope clients will impose supply-chain clauses.
- **Cyber Resilience Act:** non-commercial open-source releases of Ploeg are out of scope, but a company that sells it becomes the manufacturer. Reporting duties start 11 September 2026.
- **AI Act:** marking AI-generated commits and pull requests is advisable. A coding-agent platform is likely not high-risk; confirm with counsel.

## Decisions for the owner

1. **Confidential, phase 0:** build the pipeline now on the AX41, at no hardware cost.
2. **Where the key broker lives:** an IONOS confidential VM (option B), with a client-run broker as a premium tier.
3. **The admission carve-out** for `cc_init_data` on SNP runtime classes only, when phase 0 starts.
4. **The "before the first client" list** as the next build work after RFC 0001's delivery steps.
5. **Hardware keys:** buy them now (about €50 each; about €300 with spares and the token set for keys).
